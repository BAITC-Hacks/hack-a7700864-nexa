# Nexa

Nexa — marketplace бизнес-задач для студенческих команд, созданный для HackAlem AI. Платформа помогает бизнесу превратить свободное описание проблемы в качественный бриф, а командам — найти понятную задачу и предложить решение.

## Проблема

Бизнес часто публикует задачи без контекста, данных и критериев успеха. Студенческие команды тратят время на догадки, а качественные задачи не отличаются от сырых. Nexa делает качество постановки измеримым и поднимает лучше заполненные задачи выше в каталоге.

## Как работает решение

1. Бизнес описывает проблему обычным текстом.
2. AI задаёт ровно три контекстных вопроса.
3. Ответы превращаются в редактируемую карточку без вымышленных фактов.
4. Прозрачная формула рассчитывает рейтинг готовности 0–100.
5. После подтверждения задача публикуется и сортируется в каталоге по рейтингу.
6. Студенческая команда отправляет идею, план, срок и необязательную ссылку на прототип.
7. Бизнес вручную принимает или отклоняет каждое предложение.

## AI-функция

Server-side endpoint `/api/analyze` использует OpenAI Structured Outputs при наличии `OPENAI_API_KEY`. Ответ валидируется через Zod. Ключ загружается Wrangler из локального `web/.dev.vars` и никогда не передаётся в браузер.

Без API-ключа или при ошибке API включается детерминированный fallback. Он анализирует уже указанную информацию, выбирает ровно три недостающих аспекта и формирует карточку из описания и ответов. Поэтому полный demo flow работает офлайн.

## Рейтинг готовности

| Критерий | Вес |
| --- | ---: |
| Контекст и потребность | 20 |
| Данные и материалы | 20 |
| Ожидаемый результат | 15 |
| Критерии успеха | 15 |
| Ограничения | 10 |
| Пользователи | 10 |
| Связь с бизнесом | 10 |
| **Итого** | **100** |

Каждый критерий получает уровень `EMPTY`, `PARTIAL` или `COMPLETE`. Движок учитывает наличие обоих смысловых полей, минимальную содержательность, конкретные данные и форматы, измеримость критериев успеха, контакт и формат обратной связи. Уровни: 0–39 «Черновик», 40–69 «Рабочая», 70–89 «Готовая», 90–100 «Приоритетная». Низкий рейтинг не скрывает опубликованную задачу.

## Архитектура и стек

- Vinext / React 19 / TypeScript;
- Tailwind CSS и доступные UI-примитивы;
- server-side API routes;
- Cloudflare D1 (SQLite) и Drizzle ORM;
- OpenAI Chat Completions Structured Outputs с валидируемым fallback;
- Zod для AI-ответа и серверная очистка пользовательского ввода.

Исходный код приложения находится в `web/`. Это modular monolith со следующими границами:

- `services/ai` — OpenAI provider, structured output и deterministic fallback;
- `services/rating` — единственный источник score, breakdown, missing и рекомендаций;
- `services/tasks` — создание, изменение, подтверждение и публикация задач;
- `services/marketplace` — выборка опубликованных задач и сортировка;
- `services/proposals` — создание предложений и ручные статусы;
- `app/api` — тонкий HTTP-слой;
- `db` и `drizzle` — схема и миграции D1/SQLite.

Frontend не рассчитывает окончательный score и не управляет статусами напрямую. Сервер не доверяет score от клиента и пересчитывает его при сохранении и публикации.

Основные API-контракты:

- `POST /api/ai/analyze`, `POST /api/ai/build-card` и `POST /api/ai/diagnostic`;
- `GET/POST /api/tasks`, `GET/PATCH /api/tasks/:id`;
- `POST /api/tasks/:id/confirm` и `POST /api/tasks/:id/publish`;
- `GET/POST /api/tasks/:id/proposals`;
- `PATCH /api/proposals/:id/status`.

UI поддерживает роли «Бизнес» и «Студент» без сложной авторизации — это осознанное ограничение MVP.

## Database

- `tasks`: исходное описание, структурированные поля, score, уровень, подтверждение и публикация;
- `teams`: название, интересы, навыки и технологии команды;
- `proposals`: связь задачи и команды, идея, план, срок, прототип и ручной статус `PENDING / ACCEPTED / REJECTED`.

Миграции находятся в `web/drizzle/`. При первом открытии пустая база получает 5 демонстрационных задач, 5 команд и 5 предложений.

## Установка

Требуется Node.js 22.13 или новее.

```bash
cd web
npm install
```

Для реального AI скопируйте безопасный шаблон Wrangler:

```bash
copy .dev.vars.example .dev.vars
```

Откройте `web/.dev.vars` и вставьте ключ без кавычек, пробелов и префикса `Bearer`:

```dotenv
OPENAI_API_KEY=
```

После сохранения перезапустите `npm run dev`. Пустой ключ допустим — приложение использует fallback. Реальный `.dev.vars` исключён из Git, а `.dev.vars.example` не содержит секретов и хранится в репозитории.

Безопасная server-side диагностика доступна через `POST /api/ai/diagnostic`: режим `smoke` выполняет реальный запрос «Ответь только одним словом: OK», а режим `questions` проверяет Structured Output из трёх вопросов. Диагностика никогда не включает fallback и не возвращает API key.

## Demo scenario

1. Переключитесь на «Бизнес» и откройте «Создать задачу».
2. Введите: «Хотим автоматизировать первую линию технической поддержки».
3. Ответьте на ровно три вопроса и проверьте сформированную AI-карточку. Если OpenAI недоступен, интерфейс явно сообщает об использовании fallback.
4. Сохраните draft: backend пересчитает рейтинг и вернёт breakdown, недостающие блоки и рекомендации. Дополните слабые поля и сохраните снова, чтобы увидеть рост score.
5. Отдельно подтвердите карточку, затем опубликуйте её. Только опубликованная задача появляется в Marketplace; каталог сортируется по score по убыванию.
6. Переключитесь на «Студент», откройте опубликованную задачу и отправьте предложение команды.
7. Вернитесь в роль «Бизнес», откройте задачу и вручную нажмите «Выбрать» или «Отклонить». Статус изменится из `PENDING` в `ACCEPTED` или `REJECTED`.

## Ограничения MVP

- переключатель ролей заменяет регистрацию и RBAC;
- нет чата, уведомлений, загрузки файлов и рекомендаций;
- AI не выбирает команды и не принимает бизнес-решения;
- fallback использует эвристики и предназначен для устойчивой демонстрации;
- production hardening, аудит доступа и расширенная модерация выходят за рамки хакатонного MVP.
